# B01 — Baseline and feasibility findings

Date: 28 September 2026 · Environment: Linux container, Python 3.11.15, Node 22.22.2. **No Windows host was available.**

Everything here is reproducible with the scripts in `spikes/b01/` (see its README). The scripts import the engines from sibling checkouts at the pinned revisions.

## 1. Pinned engine revisions and test baseline

| Engine | Revision | Code size | Test result (`python3 -m unittest discover -s tests`) |
|---|---|---|---|
| pbi-doc-gen | `a7d5565cc1d237f8efc4dc96e47b756d15c1b14a` | ~9.8k lines of Python | 163 tests, OK (~2.5 s) |
| adf-doc-gen | `7c8cfe501b9d1e79eb53478779056ef9f1c9d329` | ~5.0k lines of Python | 26 tests, OK (~0.3 s) |

The Node browser checks (`tests/*.cjs`) were not run in this gate.

Repository facts that affect later work:
- Both engines use **only the Python standard library**. Neither has a `pyproject.toml`, lock file, licence file or `AGENTS.md` (the handoff asks the implementer to read `AGENTS.md`; none exists).
- Both load their HTML/JS/CSS templates from files next to the module (`Path(__file__).parent / "template.html"` etc.). Packaging (wheel or PyInstaller) must ship these as package data.
- The engines' stated minimum Python versions differ: pbi-doc-gen says 3.10+, adf-doc-gen says 3.8+ (3.10+ recommended). **Proposed platform version: Python 3.11**, the version both suites were verified on here. This still needs confirming on Windows during B09.
- pbi-doc-gen commits `pbi-tools/pbi-tools.exe` (**pbi-tools Desktop 1.2.0**, .NET Framework 4.7.2, ~10 MB) and 74 MB of Microsoft sample PBIX files (with a Microsoft sample licence). I have not verified pbi-tools' licence here. It is reportedly AGPL-3.0, which would matter for bundling. **Decision needed before B09:** keep pbi-tools as an externally installed prerequisite (the handoff's default), not bundled.

## 2. Output shape and representative sizes

Synthetic samples were generated by the engines' own sample builders (`tests/samples/build_*_sample.py`) and the ADF example factory. Real PBIX samples could not be extracted because pbi-tools needs Windows and Power BI Desktop, so **real-world sizes remain unmeasured**.

| Document | HTML bytes | Embedded payload bytes | Searchable names* bytes |
|---|---|---|---|
| PBI Retail Sales (model + report) | 402,049 | 256,963 | 1,699 |
| PBI Network Operations | 333,940 | 188,789 | 1,274 |
| PBI Field Services | 297,222 | 152,073 | 1,149 |
| PBI Finance Model (model only) | 291,224 | 145,940 | 980 |
| ADF contoso-sales-etl | 148,968 | 50,620 | 804 |

\*Titles plus table, column, measure, page, source, pipeline, activity, entity and trigger names: a lower bound for a useful index entry.

- Both engines embed their native payload as executable JavaScript (`const DATA = {...};`) in the main script, escaping `</` as `<\/`. Only the small user-details block is an inert JSON script (`pbi-documentation-metadata` / `adf-documentation-details`). The contract's inert `pbidoc-manifest` element is therefore new work for both renderers.
- Native `schemaVersion` is `2` in both engines, independent of the envelope `schema_version` 1.
- `generated` is formatted `YYYY-MM-DD HH:MM UTC`, not RFC 3339. The envelope must produce its own `generated_at`.
- **Index budget:** names alone are ~1–2 KiB per document, well inside the ~20 KiB/document browser-index budget. Adding prose, descriptions and DAX/SQL text could exceed it. Re-measure with real PBIX output before accepting browser-only search.

## 3. Safe-publication probe — fails (as the review predicted)

`probe_pbi_secrets.py` seeds five markers into Power BI partition M expressions. **All five appear in both the HTML and the JSON output:**

| Seeded content | In HTML | In JSON |
|---|---|---|
| ODBC `Pwd=` in a connection string | yes | yes |
| Literal in a native SQL query | yes | yes |
| Entered-data row (`Table.FromRows`) | yes | yes |
| Compressed entered-data body (`Binary.FromText` base64) | yes | yes |
| Token in a `Web.Contents` URL query string | yes | yes |

The Power BI payload also embeds `model.sourcePath`, the **absolute machine path** of the input model. The handoff forbids that in published artifacts.

`probe_adf.py` seeds the ADF engine:

| Seeded content | Result |
|---|---|
| Inline `Password=` in a linked-service connection string | redacted |
| SAS `sig=` in a linked-service URI | redacted |
| Literal in a Lookup `sqlReaderQuery` | **leaks** in HTML and JSON (the lineage edge `detail` and activity `query`) |

Conclusion: ADF has a working redaction layer (`adfdocgen/redact.py`) that covers credentials but not query literals. Power BI has none for M. A projection layer in the adapter (B03) is required for both. Withholding raw M/SQL by default, as section 17.1 requires, removes all observed leaks. It also removes the M text shown in the Power BI Sources view. The structured `sourceObjects` (server/database/object) remain, and they carry most of the relationship value.

## 4. Endpoint identity probe — fails in the engine, not only the bridge

`probe_adf.py` builds a factory with two linked services on `sql1.corp.local` ports **1433** and **1444**, each written to `dbo.Sales` by a different Copy activity, plus datasets on `raw/Sales/Daily` and `raw/sales/daily`, and a Delete activity.

| Check | Expected | Observed |
|---|---|---|
| Two `dbo.Sales` tables on different ports | 2 entities | **1 entity** `table:sql1.corp.local/dw/dbo.sales` (port stripped by `common._norm_host`) |
| SQL database/object case | preserved unless collation known | **lowercased** in the entity key (`dw/dbo.sales`) |
| Case-distinct lake paths | 2 entities | 2 entities (the engine preserves path case) |
| Delete activity | distinct `deletes` operation | recorded as a **`sinks`** entry with `mechanism: "Delete"`. `bridge.py` then groups it with writers |

This confirms the handoff's section 16/17.2 warning: fixing only `bridge.py` is insufficient. The port merge happens in `common.physical_key`/`_norm_host` before aggregation. The bridge's path lowercasing (`bridge.py` lines 66, 95–97) is a separate, second defect.

## 5. Stable identity survey

Neither engine emits explicit object IDs. Current natural keys:

| Engine | Objects | Current key | Stability risk |
|---|---|---|---|
| Power BI | tables, columns, measures | names (measures also carry `table`) | Rename = new object; no durable ID in PBIP/TMDL except `lineageTag` (not surfaced by the parser; **investigate in B02**) |
| Power BI | sources (`sourceObjects`) | no ID; server/database/object/location plus `primaryQuery`; rows also carry `pageId` usage | Logical source and page usage are mixed in one row. B02 must split them as section 17.2 requires |
| ADF | pipelines, triggers, datasets, linked services, data flows | resource `name` | Native names are unique per factory and reasonably durable |
| ADF | activities | `activity` name within its pipeline, plus `scope`/`depth` for nesting | Needs pipeline + container-path composite ID |
| ADF | entities (physical endpoints) | `key` = normalized physical key | Unsafe as-is (§4); needs versioned normalization |

The PBI `lineageTag` lead is the most important B02 input: if it survives TMDL/BIM parsing, it gives durable table/column/measure identity.

## 6. Legacy-import feasibility — feasible

`extract_native.py` identifies the engine from its details-block ID and decodes the single `const DATA = ` literal with `json.JSONDecoder.raw_decode`, **without executing any script**. It works on all five documents. The recovered payload matches the engine's `--json` output except for the renderer-added fields `documentationFilename` (both) and `details` (ADF). Zero or multiple `DATA` markers are rejected. This makes the section 5 path ("extract native data without evaluating scripts, project, re-render") practical for documents produced by these engine versions.

## 7. Viewer feasibility — partially assessed

- Both native viewers are single-file HTML apps with inline JS/CSS and no external requests (by design, "works offline"). They can therefore be served inside a sandboxed iframe (`sandbox="allow-scripts"`, no `allow-same-origin`) with a CSP that blocks network access. That still needs a browser test in B06.
- Both viewers include editing features (the report/factory details editor saves a new HTML file). The hosted read-only mode must disable these (A37). The switch point is the renderer's details-block injection.
- Object-level navigation hooks (postMessage `navigate-object`) do not exist yet; they are B06 work in each template.

## 8. Windows packaging feasibility — **UNVERIFIED**

No Windows host is available in this environment. Nothing here proves a working installer. What can be said from source:
- Standard-library-only engines plus pywebview (Edge WebView2 on Windows) and PyInstaller is a low-dependency stack. The main packaging risk is including the template data files and the WebView2 runtime prerequisite.
- PBIX extraction needs Power BI Desktop plus pbi-tools Desktop (.NET Framework 4.7.2) on the machine. Those are external prerequisites for `doctor` to detect, not bundled.

**Open gate:** B01 packaging spike (a PyInstaller + pywebview hello-app that loads an engine template and runs one PBIP generation) must be run on a Windows machine or Windows CI runner. Until then, B09 remains blocked on environment.

## 9. Decisions and questions raised

1. **Python 3.11** proposed as the platform version (confirm on Windows).
2. **pbi-tools stays an external prerequisite**; confirm its licence before any redistribution.
3. **Power BI M/SQL withholding (open question for the product owner):** the default safe profile removes the M/SQL text currently shown in Power BI Sources views. Keep that default for R1, or fund a supported M sanitizer?
4. Engine packaging: B02/B03 should add a `pyproject.toml` to each engine (upstream PR) or vendor them as pinned git dependencies. Upstream packaging is recommended; it is a small change and keeps the engines authoritative.
5. The adversarial-review document referenced as F01–F14 (`BI-Documentation-Platform-Adversarial-Review.md`) is not in this repository. Findings here were re-derived independently.
